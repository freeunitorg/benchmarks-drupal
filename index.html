Application-server benchmarks: Drupal, Symfony, WordPress and plain PHP

An instruction-count comparison of the same application on several runtimes, one job at a time, with the measurement noise bounded before any claim is made. Read the findings in prose.

Overview (72) Drupal 11.4 (16) Drupal 11.5 (5) Drupal 12.0 (25) Symfony (4) WordPress (12) Framework-free PHP (6) ARM64 (Oracle A1) (4)

Everything here is rebuilt from committed results/<run-id>/summary.json files. The null band is printed beside every comparison: it is the same job run with both sides identical (A against a copy of A), so a delta smaller than the band is noise and is reported as no claim. Host class, governor, PHP, Drupal tag, database and runtime versions are in each run's header.

The short version

This page holds 72 published comparisons across 9 application sites, measured on aarch64-2c, unrecorded, x86-48t-shared, x86-perf-a, x86-perf-b. Each comparison is one job: the same cells against two runtimes, with a null phase that bounds the noise first. A CLAIM appears only when the delta is outside that band. Start with the summary tables, then open a run for its numbers; every run links to its raw results/<run-id>/ directory.

Cron and queue arms: cold CLI against the HTTP path

One row per arm from the raw ticks.tsv. Arm A is a cold one-shot CLI process (drush core:cron / queue:run, or the equivalent bench command on Drupal 12), arm B is GET /cron/{key} served by a normal web worker. The CLI arm runs before the web workers are warm, so its wall time is the one to read; the HTTP arm returns before the job finishes on FreeUnit (it detaches), which is why its wall time is the trigger latency.
