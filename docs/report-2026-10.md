# Drupal, Symfony and bare PHP on three application servers

A plain-language summary of what the benchmark found. The numbers are the published
runs at https://freeunit.org/benchmarks-drupal/, which rebuilds from committed
`results/<run-id>/summary.json` files; each claim below quotes the published headline
verbatim in spirit and links to the run that produced it.

Measured 2026-10-10/11 on two identical hosts (Intel Xeon E3-1245 v5, 8 threads,
`powersave` governor): Apache 2 with `mod_php`, nginx with PHP-FPM, and FreeUnit, all
serving the same PHP 8.5.11 build and the same site, one job at a time.

## How to read it

* The metric is **retired instructions on the server** per request, from hardware
  performance counters, not wall-clock time and not a synthetic score. It answers
  "how much work does the server do to serve this request", which is what a runtime
  can change; wall time on a shared box answers mostly "who else was running".
* Every job **bounds its own noise first**: a *null phase* runs both sides as the same
  runtime (A against a copy of A) and turns that difference into a band. A delta inside
  the band is reported as **no claim**, and that is a result, not a missing one.
* Jobs run one at a time, and the load generator and the server are pinned to disjoint
  CPUs, so a comparison is controlled even though the absolute numbers are not
  comparable across jobs.

## What it found

**On a Drupal front page served from the page cache, PHP-FPM needs more server work
than FreeUnit.** With Drupal 11.4's demo content, nginx + PHP-FPM spends 7.7 % more
instructions per request than FreeUnit 1.37.0, and the same 7.7 % against FreeUnit
master. The result repeats on the `standard` profile (6.8 %) and on Drupal 12 (10.3 %),
so it is not one site's shape.

**Apache with mod_php is much more expensive than either.** 54.7 % more instructions
than nginx + PHP-FPM on the same page (and 66.8 % more than FreeUnit master). If the
question is "which of the three does the least work per request", it is not close.

**Symfony shows the same ordering, smaller.** FPM 5.8 % above FreeUnit on both the
1.37.0 and master sides.

**With no framework in the way, the gap becomes the whole picture.** A PHP script that
returns headers or a small body costs nginx + PHP-FPM **97 %, 108 % and 196 %** more
instructions than the same script under FreeUnit (three separate cells: headers, hello
and body). This is the per-request plumbing — FastCGI, a second process tree, the
proxy — and it is the floor under every framework number above; a framework hides
part of it, it does not remove it.

**On the authenticated page the runtimes are effectively tied, and the reason is
measurable.** FreeUnit 1.37.0 needs 0.6 % *fewer* instructions than FPM there; FreeUnit
master lands inside the noise. A decomposition job that splits the cost into the front
proxy tree and the PHP worker tree found the difference is **cycles and context
switches, not instructions or database work** — the database counters move by a third
of a percent. On Drupal 12 the sign flips: FPM is 0.3 % *ahead* on the authenticated
page. The honest summary is that the authenticated page is application- and
database-bound, and the runtime's share of it is at the edge of what these cells can
resolve.

**FreeUnit master and 1.37.0 are indistinguishable here** (no claim on both the
anonymous and authenticated pages), and the "direct routes" variant is no faster on
the cached page (no claim), which is what a page-cache hit predicts.

**Cron and queue work is not a request-path problem.** A cold one-shot CLI run
(`drush core:cron` and friends) takes 5.90 s on average across 20 ticks, while the HTTP
path that triggers the same work returns in 0.70–0.73 s on all three runtimes — FreeUnit
detaches the request, so its 0.73 s is the trigger latency, not the job. Across 20 ticks
none of the three grew its process count: the leaked-process bug these arms were written
for stays fixed.

## Notes from building this

Two Drupal 12 surprises that cost real runs and are now written down as harness
findings:

* **Drupal 12's `standard` profile is not a usable site on its own.** An installed
  `12.0.0-beta1` has no `node.type.*`, no node view displays and no frontpage view; its
  front page is `/admin/welcome`, which anonymous users cannot see. 11.4 shipped a
  working content model and `front: /node`. On 12 the content has to come from a recipe
  (or from the `demo_umami` profile), so the benchmark's `12.0-standard` arm was dropped
  rather than measured on nothing.
* **FreeUnit cannot set `opcache.preload` or `opcache.jit` per application**:
  they are `PHP_INI_SYSTEM` settings and `applications.*.options.admin` is applied after
  PHP starts. Until that changes, per-application preloading and JIT need a baked or
  mounted `php.ini`.

## Reproduce it

```sh
git clone https://github.com/freeunitorg/benchmarks-drupal && cd benchmarks-drupal
bin/drupal-bench build                       # the three runtime images
bin/drupal-bench site 11.4                   # install a site
bin/drupal-bench run bench/jobs/02-front-anon-freeunit-vs-fpm.job
scripts/collect.sh && python3 report/render.py results public/index.html
```

Each run writes `results/<run-id>/` with `summary.json` (the numbers),
`compare.txt` (the verdict), `results.tsv` (every cell), `meta.txt` (host, governor,
versions) and `cells.log` (the raw per-cell lines). `docs/state.md` is the resume note
for the whole suite; `docs/drupal-perf-opportunities.md` lists what was tried for
performance beyond the runtimes themselves.

## Caveats

* The two hosts are shared with other work, so published runs are the ones that passed
  their own null band and a quiet-box gate; runs that came back `INVALID` or `NO DATA`
  are deliberately not published.
* The absolute means in the cross-run summary are pooled from runs taken hours apart
  under a `powersave` governor. Use that table for the ordering; the per-run tables are
  the controlled measurement.
* PHP-FPM and Apache are configured the way a Drupal production site would be, not
  tuned for the microbenchmark; the framework-free cells should be read as the shape of
  the per-request overhead, not as a configuration verdict.
